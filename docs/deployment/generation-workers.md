# 生成任务 Worker

| 元信息 | 内容 |
| --- | --- |
| 维护状态 | 生产使用 |
| 目标读者 | 后端开发与运维人员 |
| 事实来源 | API 队列实现、PM2 配置与生产工作流 |

## 概述

生成任务通过 Redis 与 BullMQ 解耦请求接收和耗时执行。API 创建任务并向客户端发送状态，Worker 消费队列并按流水线更新运行记录。

## 当前设计或配置

### 角色

- API：校验权限与前置条件，创建运行记录并入队。
- Worker：领取任务，调用领域流水线，写入阶段事件和终态。
- Redis：保存队列、租约和重试协调信息。
- PostgreSQL：保存项目数据、任务记录和可恢复业务状态。

### 并发

全局、供应商、项目、用户和单次运行并发均由 `UML_LLM_*` 环境变量控制。生产值应根据模型供应商限流、服务器资源和任务时长压测确定，不能直接照搬开发环境。

设计顺序图按用例并行。顺序图完成后，总体架构、设计类图和导航并行；数据库和组件等待设计类图，部署等待组件。失败只阻断依赖它的分支。可行性环境图与业务流程并行，实现方案等待两个已校验产物。说明书使用固定目录和共享术语，按一级章节分组，最多四组并行，仍受现有模型调用上限约束；各组保留两轮修复预算，按模板顺序合并后执行整篇检查和 DOCX 导出。

结构、确定性绘制、图片检查仍完整执行。只在同一运行内复用模型、依据、图片、供应商和检查版本完全相同的已通过检查。调用进度与遥测使用每次调用自身的阶段和子任务，避免并行分支串用当前阶段。

## 操作与维护

- 部署前确认 `REDIS_URL` 可用，并限制为可信网络访问。
- 调整并发时同时观察队列等待、供应商限流、数据库连接池和内存。
- 修改重试策略时区分可重试网络错误、供应商限流和不可重试输入错误。
- 发布或重启时保留数据库记录，避免把运行中的任务误标为成功。
- 主生成和任务抽屉订阅 `view=progress`，界面每 100 毫秒合批，终态立即刷新；收到完成事件后读取完整快照再应用产物。全文仍保存在后端历史。历史与 SSE 支持可选 `afterSequence`，历史响应提供 `cursor`，旧客户端可继续读取全部事件。
- 生成、保存、恢复和指纹统一清理明确属于已删除用例的分析模型。设计完成不会回写覆盖当前需求；开始时记录设计分支指纹，期间被人工修改或其他任务替换的分支保留当前内容，完整生成结果留在历史。
- 来源误报的定向修复使用 `scripts/maintenance/design-source-repair.mjs`。先指定项目、原任务、旧版本契约和备份路径预览，核对有效来源、模型、图源、SVG 和原指纹一致后，使用 `--apply --expected-version` 条件更新。工具只修改已证明错误的来源指纹，保留历史及检查结论，并写入审计记录。

## 验证

1. 创建生成任务并确认状态从排队进入运行。
2. 检查阶段事件、SSE 终止事件和最终产物一致。
3. 模拟供应商超时并验证重试及失败信息。
4. 重启 Worker 后验证遗留任务按当前恢复策略处理。
5. 契约测试覆盖 26 个来源清理为 15 个以及真实修改仍改变指纹；API 测试覆盖依赖等待、失败分支隔离、人工修改保护、严格检查复用和模拟耗时至少减少 30%；Web 测试覆盖三万条正文事件不积累与游标恢复。
