# 可信生成链路

| 元信息 | 内容 |
| --- | --- |
| 维护状态 | 持续维护 |
| 目标读者 | 产品、开发、测试与课程验收人员 |
| 事实来源 | 生成流水线、运行记录、覆盖矩阵与应用内手册 |

## 概述

平台将需求、可行性、UML、设计、代码、测试和说明书视为有依赖关系的产物链。可信度来自明确的上游基线、可定位的生成记录、结构化校验和必要的人工确认，而不是仅依赖模型回答。

## 当前设计或配置

### 基线与前置条件

需求规则和修复候选需要确认后才能形成稳定输入。下游按钮同时在界面状态与操作守卫中检查前置条件，并展示阻塞原因。

### 运行证据

生成任务保存阶段、状态、事件、错误和可恢复快照。完成结果通过元素 ID、需求规则和上游引用形成映射；失败结果保留可排查信息，而不伪装为成功产物。

### 结构与覆盖

模型输出先经过按阶段契约与公共语义校验，结构错误最多修复两轮。通过后确定性生成 PlantUML，不允许 LLM 改写最终源码；图像审查仅作辅助反馈。追踪矩阵和覆盖关系用于发现未覆盖、低置信或断开的链路。

### 人工责任

模型输出仍需人工评审。尤其是需求边界、架构取舍、成本数据、安全结论和验收标准，应由项目成员确认后再作为正式交付依据。

### 固定演示数据

离线演示项目由 `UML_DEMO_OFFLINE_PROJECT_IDS` 或 `UML_DEMO_OFFLINE_PROJECT_NAME_PATTERNS` 指定。座位预约场景提供系统环境图、业务与系统流程图、两套实现方案及补充资料，经过正式可行性管线的结构、追踪和输入指纹校验后保存。成本和周期属于固定示例估算。

演示项目在可行性分析概览选择产物后生成；已有数据遵循相同的过期与依赖规则。固定演示使用随代码保存的 SVG，不调用真实模型或渲染服务，也不扣除生成额度。运行保存演示标记，刷新、重试和重新运行后仍使用固定数据。可行性报告保留已校验的环境图与方案，不替换为其他阶段的演示模型。

## 操作与维护

项目详情通过只读 `generationExecutionMode` 返回 `offline-demo` 或 `provider`；旧响应缺省按真实模型模式处理。演示模式由服务端项目配置决定，前端只对已确认的演示项目使用固定模型占位值。需求、可行性分析、设计、代码与 AI 报告共用模型校验：真实项目必须选择有效供应商及其目录中的模型，缺失或失效时禁用生成并显示原因；模型选择控件保持可用。设置读取不会自动把空模型或已下线模型替换为目录第一项。刷新和切换项目重新加载运行模式；后端仍独立拒绝真实项目提交的演示占位配置。测试模型使用本地规则，无需模型；历史任务重试继续使用任务保存的配置。

1. 先确认需求文本、规则和质量提示。
2. 生成并检查可行性与需求模型。
3. 在设计、代码、测试和文档阶段检查映射与覆盖。
4. 出现失败时从运行历史定位阶段、错误和修复记录。
5. 修改上游后重新验证受影响的下游产物。

## 验证

- 运行 API、Web 和端到端测试。
- 检查每个成功任务都有终态事件和可定位产物。
- 检查失败、重试和恢复不会覆盖已确认的基线。
- 在应用内手册中核对入口、前置条件、产物和映射说明。
