# 可信生成链路

| 元信息 | 内容 |
| --- | --- |
| 维护状态 | 持续维护 |
| 目标读者 | 产品、开发、测试与课程验收人员 |
| 事实来源 | 生成流水线、运行记录、覆盖矩阵与应用内手册 |

## 概述

专业版将需求、可行性、UML、设计、测试和说明书视为有依赖关系的产物链。可信度来自明确的上游基线、可定位的生成记录、结构化校验和必要的人工确认，而不是仅依赖模型回答。普通版采用[项目 Agent 会话](standard-project-agent.md)，只检查图结构，不执行本页所述依赖及过期机制。

## 当前设计或配置

### 基线与前置条件

需求规则保存后形成稳定输入；生成候选通过后端结构与来源校验后发布。下游按钮同时在界面状态与操作守卫中检查前置条件，并展示阻塞原因。

需求基线仅包含 `schemaVersion`、`id`、`version`、`rules`、`runId`、`sourceInputFingerprint` 和 `createdAt`。每条规则保存 `id`、`requirementId`、`type`、`text` 与可选的 `sourceFragment`；不再保存假设、冲突、质量报告、来源文档占位标识或生成/人工修改分类，也不保存工作区重复质量报告。需求抽取只校验来源、完整性和关键事实，不生成启发式质量提示。带有已删除字段的旧数据在当前边界被拒绝，不自动转换或补造来源。

需求基线保留在后端，用于版本、输入指纹、过期判断和发布守卫，不进入模型生成 Prompt。每个任务固定一份绑定资料，由任务 Prompt 在首次生成请求中提供一次，共用会话不再额外拼接上游副本，后端校验使用相同范围。修复时只追加本轮错误反馈，沿用原会话中的资料和模型结果，不重复附带原文、来源目录、候选副本或通用指令。模型直接返回完整 JSON，不通过 function calling 查询资料、发起校验或提交产物。绑定 `r1、r2` 时只提供这两条规则，不能通过基线补入 `r3`，也不按规则类型隐式排除已绑定规则。

普通需求模型使用绑定的需求规则；需求分析顺序图使用目标用例及其明确关联的用例上下文。可行性系统环境图与业务流程图使用绑定规则及补充资料，实现方案再加入绑定的系统环境图和业务流程图。设计任务按当前模型依赖绑定需求模型及直接上游设计模型，不额外查询独立需求规则；模型内的需求规则 ID 只能继承绑定上游中已有的 ID。

### 运行证据

生成任务保存阶段、状态、事件、错误和可恢复快照。完成结果通过元素 ID、需求规则和上游引用形成映射；失败结果保留可排查信息，而不伪装为成功产物。

### 结构与覆盖

生成 Prompt 中的模型 JSON Schema 和供应商响应 Schema 从同一模型契约投影。需求分析模型的每个嵌套元素必须提供非空来源数组；系统环境图的系统、人员、外部系统及关系必须提供需求规则来源。严格响应中的可选字段用 `null` 占位，后端按现有字段契约处理，不将占位值当作真实来源。跨元素引用和来源真实性仍由后端校验。

模型返回完整结果后，后端对该候选执行一次 JSON、Schema 和来源映射校验；失败就在原会话中追加本轮错误，保留原始上游资料和完整候选，要求返回修正后的完整 JSON。校验通过后编译 PlantUML 源码，确定性的源码编译错误也反馈到同一会话；不对相同候选连续重建，也不重复附带上游来源列表。编译与生成修复共用每模型五次修复预算。绘图服务的运行故障保留重试恢复机制。抽屉分别记录后端校验、源码编译失败、模型修复、编译通过和最终绘制保存，历史失败不会被后续成功覆盖。

模型输出先经过阶段契约、结构及来源校验。引用按对应模型中真实存在的元素 ID 匹配，业务元素需要完整声明来源；不使用映射置信度或待确认状态作为门槛。生成修复、后置结构修复和绘图重试按同一模型共享最多五次修复预算。后置修复在原生成对话中追加反馈，返回完整模型及来源映射；重新校验并完成绘图后一起发布。通过后确定性生成 PlantUML，不调用 LLM 改写最终源码或进行额外看图审查。追踪矩阵用于定位来源，不代表所有上游需求都已被实现。

### 人工责任

模型输出仍需人工评审。尤其是需求边界、架构取舍、成本数据、安全结论和验收标准，应由项目成员确认后再作为正式交付依据。

### 固定演示数据

离线演示项目由 `UML_DEMO_OFFLINE_PROJECT_IDS` 或 `UML_DEMO_OFFLINE_PROJECT_NAME_PATTERNS` 指定。座位预约场景提供系统环境图、业务与系统流程图、两套实现方案及补充资料，经过正式可行性管线的结构、追踪和输入指纹校验后保存。成本和周期属于固定示例估算。

演示项目在可行性分析概览选择产物后生成；已有数据遵循相同的过期与依赖规则。固定演示使用随代码保存的 SVG，不调用真实模型或渲染服务，不请求模型供应商。运行保存演示标记，刷新、重试和重新运行后仍使用固定数据。可行性报告保留已校验的环境图与方案，不替换为其他阶段的演示模型。

## 操作与维护

项目详情通过只读 `generationExecutionMode` 返回 `offline-demo` 或 `provider`；当前响应必须明确提供模式，缺失时拒绝读取。演示模式由服务端项目配置决定，前端只对已确认的演示项目使用固定模型占位值。需求、可行性分析、设计与 AI 报告共用模型校验：真实项目必须选择有效供应商及其目录中的模型，缺失或失效时禁用生成并显示原因；模型选择控件保持可用。设置读取不会自动把空模型或已下线模型替换为目录第一项。刷新和切换项目重新加载运行模式；后端仍独立拒绝真实项目提交的演示占位配置。测试模型使用本地规则，无需模型；历史任务重试继续使用任务保存的配置。

来源映射每项只保留必要引用：需求模型使用 `ruleId`、`target`，设计模型使用 `source`、`targets`；设计的直接上游无论属于需求模型还是设计模型，均统一记录在 `targets` 中。映射契约不再包含 `mappingSource`、`rationale`、`upstreamDesignRefs`、`reviewStatus`、`confidence` 或旧值 `auto-filled-pending-review`。含这些旧字段或旧枚举值的保存数据会在当前契约边界被拒绝，不自动迁移，也不改写其来源。可行性方案的业务论证、风险与假设仍按方案契约保留。

1. 先核对需求文本、规则与原文依据。
2. 生成并检查可行性与需求模型。
3. 在设计、测试和文档阶段检查映射与覆盖。
4. 出现失败时从运行历史定位阶段、错误和修复记录。
5. 修改上游后重新验证受影响的下游产物。

## 验证

- 运行 API、Web 和端到端测试。
- 检查每个成功任务都有终态事件和可定位产物。
- 检查失败、重试和恢复不会覆盖已确认的基线。
- 用普通 JSON 生成测试核对首次绑定资料、规则子集、越界映射拒绝、同会话修复及基线元数据保留；测试入口为 API 的 `model-generation-session.test.ts`、`model-source-scope.test.ts` 和 `feasibility-pipeline.test.ts`。
- 在应用内手册中核对入口、前置条件、产物和映射说明。
