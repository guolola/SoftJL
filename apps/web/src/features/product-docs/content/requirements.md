# 整理需求与确认规则

## 适用场景

把业务描述拆成可检查的需求规则，为分析、建模、测试和说明书准备共同依据。

## 入口位置

项目左侧 **系统需求**。文本输入区用于说明业务，规则列表用于检查与修正生成结果。

## 前置条件

项目可编辑，且已选择可用的供应商与模型。需求至少应说明 **谁使用、要完成什么、有什么限制、失败时怎么办**。

## 操作步骤

### 1. 输入具体的业务需求

例如：

```text
学生登录后可以查询空闲座位，选择日期和时间段提交预约。
同一学生同一时间段只能有一条有效预约；重复提交时提示原因。
管理员可以维护座位并处理异常取消。预约成功或取消后通知学生。
```

### 2. 生成并逐条检查

点击 **提取需求规则**（修改已有需求时显示 **更新需求规则**），检查功能需求、业务规则、数据需求、异常处理和非功能需求。对照原文，确认没有遗漏限制，也没有加入未要求的功能。

![系统需求页：输入业务描述，使用提取需求规则，并逐条检查需求规则](/help/images/docs-requirements-current.png)

### 3. 处理质量提示和修复候选

打开规则的质量提示，查看需要确认的原因。无需修改时可选择 **确认提示**；需要补充内容时使用 **智能修复**。出现修复候选后，比较修改前后内容，再选择 **采纳** 或 **拒绝**。

> [!NOTE]
> AI 给出的补充是候选内容。只有符合你的业务意图，才应采纳；待确认项需要处理后才能继续相关生成。

![需求质量提示：先读清楚原因，再选择智能修复或确认提示](/help/images/docs-requirement-quality-detail.png)

### 4. 继续分析或建模

查看生成按钮附近是否还有阻塞提示。规则可用后，进入[可行性分析](feasibility-analysis.md)或[需求模型](uml-models.md)。

## 结果与产物

得到可追踪的需求规则、质量提示和已确认的需求版本。文档中的“需求基线”就是后续阶段使用的那一版需求依据。

## 映射关系

例如“同一时间段不能重复预约”会成为流程中的校验分支、数据约束和重复提交测试的依据。模型生成后，可在 **跟踪矩阵** 查看实际映射。

## 常见问题

**修复失败？** 根据提示手动补充角色、触发条件、输入输出或异常情况，再重试。

**修改原文后还能用旧规则吗？** 旧规则可能不再覆盖最新文本。查看 **需求已修改** 提示，重新生成或确认规则。

**规则太笼统？** 将“系统要好用”改成可检查的行为，例如“预约失败时保留已选时间段，并显示失败原因”。

**仍无法生成模型？** 继续阅读[处理需求待确认项](requirement-baseline.md)。
